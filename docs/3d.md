# 3D: RAVE, QuickDraw 3D and OpenGL

Mac OS 8.5 to 9 programs draw in 3D in two ways: through QuickDraw 3D RAVE,
which QuickDraw 3D's interactive renderer and most games of the time use,
and through OpenGL 1.x with AGL, its Mac binding, which later games use.
The iMac's ATI chip accelerated both. Blue has a RAVE engine of its own
and OpenGL libraries of its own, both guest tools (installed as in
[guest-tools.md](guest-tools.md)), whose work is done on the host, where
one 3D backend draws for both: the host's GPU in real time, a software
rasterizer otherwise. This document describes how. How to use them is in
the [README](../README.md#the-guest-tools); how particular games use them
is in [software.md](software.md#bugdom-and-unreal-tournament).

```
QuickDraw 3D, RAVE games                      OpenGL games (AGL)
        │                                            │
Blue 3D Engine (a RAVE engine)          Blue OpenGL Library, Memory, Utility
  every method a host call                most gl calls recorded in guest
        │                                 memory, the rest host calls
   src/rave.c                                        │
        │                             src/opengl.c, the front end (glfront.c...)
        └──────────────── the 3D backend ────────────┘
          raster.c (software)  or  gpu.c (OpenGL 3.3 core, on its own thread)
                                    │
     each frame into guest memory (the screen, a window, a GWorld), paced
```

Everything below the libraries is C on the host. The backend draws from
screen-space commands, so RAVE (whose vertices are in screen space
already) and OpenGL (whose front end transforms, lights and clips them
first) share it, and frames go back into guest memory, where QuickDraw and
the rest of Mac OS see them, screenshots include them, and runs in
instruction time reproduce them.

## QuickDraw 3D and RAVE

QuickDraw 3D RAVE finds drawing engines in the Extensions folder (files of
type `shlb` and creator `tnsl`) each time a program loads it, so a
program opened after the engine is installed finds it without a restart,
even after another program has loaded RAVE. Blue 3D Engine is such a
fragment, generated like Blue's drivers (`src/ndrv.c`); its initialization
routine registers it with `QARegisterEngine`, and every method is a host
call to `src/rave.c`. QuickDraw 3D's interactive renderer, and RAVE games,
then find an accelerator.

- **It says it's ATI's** (vendor 1, engine 5): games of the time, Bugdom
  among them, take a RAVE engine for hardware only if it's ATI's. It
  answers ATI's private tags as far as games use them: tag 1011, the
  hardware's generation, is 0x500 (a Rage 128), and tag 1021 gives ATI's
  table of extensions, which Unreal Tournament calls without checking
  (clearing the draw and z buffers, replacing a texture's pixels); tag 1018
  is a second texture (a lightmap) that modulates the first while tag 1012
  is on, at coordinates in the vertices' specular fields.
- **Contexts** draw to a screen (a GDevice) or to a memory device, with
  Z buffering, Gouraud shading, perspective-correct and mipmapped textures
  (modulate, decal, highlight), fog, the alpha test, RAVE's blend modes and
  OpenGL-style factors, and depth-sorted transparency. Textures and bitmaps
  (16- and 32-bit formats) are converted to the host's `0xAARRGGBB` once,
  when they're made, and kept on the host. `accessTexture`,
  `accessDrawBuffer` and `accessZBuffer` aren't supported.
- **Recording:** each call becomes backend commands (triangles, lines,
  points, bitmaps, clears), each with its state, in batches of 512; a full
  batch is drawn in the background while the guest records the next.
  `renderStart`'s clear is the frame's first command, so both backends
  clear alike. Triangles marked transparent with `kQATag_ZSortedHint` are
  held back and drawn last, sorted by depth. At the frame's end the rest is
  drawn and the frame is copied into the context's device in guest memory,
  converted to its 16- or 32-bit big-endian pixels and clipped to the
  bounding box of the context's clip region.
- **RAVE's texture operations** are the backend's stages
  (`raster_rave_stages()`): the texture decaled over the vertex colour, or
  its alpha times the colour's; then times kd (modulate); then times the
  second texture if there is one (ATI's multitexturing), or else plus ks
  (highlight).
- **The engine's data carries its version**, so one installed by an older
  Blue isn't asked for what it lacks: Blue says to install it again.

## The 3D backend

### What it draws

`src/raster.h` defines what both backends take. A vertex has x and y in
pixels (x right, y down, pixel centres at half-integers), a depth, 1/w,
three colours (the primary one; OpenGL's secondary colour, or RAVE's kd and
ks), a fog coordinate, and each of two texture units' s, t, q and r.
Everything after x and y is interpolated linearly in screen space, so what
is to be perspective-correct comes divided by w (the texture coordinates
and the fog coordinate), and is divided per pixel by the interpolated 1/w,
or by a unit's q/w. A state has:

- two texture units (OpenGL's six filters, clamping or repeating in each
  coordinate, 2D or 3D textures), combined in up to four stages as
  `GL_COMBINE` does (replace, modulate, add, add signed, interpolate,
  subtract; arguments from the stage before, the colours, either unit's
  texture or a constant, each as it is, its alpha in every channel, or one
  minus that; scaled by 1, 2 or 4 and clamped);
- depth functions, testing z or (RAVE's "perspective z") 1/w; the stencil
  test and its operations, in OpenGL's order (alpha, stencil, depth);
- the alpha test; blending by RAVE's premultiply and interpolate, by
  OpenGL's factors and equations (add, subtract, reverse subtract, min,
  max, with the constant colour), none, or a logic operation; colour
  masks;
- fog by alpha (RAVE's), linear, exp or exp², by w or the fog coordinate;
- a clip rectangle; points and lines drawn as RAVE's or by OpenGL's rules
  (antialiased, stippled), the polygon stipple, and each unit's
  level-of-detail bias and limits;
- whether fragments with alpha 0 are drawn (as OpenGL draws them) or leave
  depth, and colour unless they add some, alone (as hardware RAVE engines
  skip transparent texels).

### The software rasterizer

`src/raster.c` is the reference: in instruction time it draws everything,
and its pixels are the same on every host and however many threads draw
them.

- **Edges are exact.** Vertices snap to 1/256 of a pixel, as GPUs and
  Mesa snap them, and edge functions are 64-bit integers there, with the
  top-left rule as a bias of 1 (vertices beyond 2^21 pixels aren't drawn);
  each row's span comes out by integer division, so pixels aren't tested
  one by one. Triangles sharing an edge leave no gap and draw no pixel
  twice. With float edge functions, both triangles' could come out just
  negative at a centre exactly on a shared edge, and neither drew it.
- **No fused multiply-adds.** clang contracts `a * b + c` into one
  operation by default, and did 345 times in `raster.c` on Apple silicon,
  where it rounds once instead of twice, so Apple silicon's pixels
  differed from Linux's and Intel Macs'. `#pragma STDC FP_CONTRACT OFF`
  stops clang; GCC ignores the pragma, and contracts nothing in ISO C mode
  (`-std=c11`), so `CFLAGS` given on make's command line, which replace the
  Makefile's, must keep it (CI gives them in the environment).
- **Mipmapping is per triangle** (a line's level from its texels a pixel),
  where a GPU picks a level per pixel.
- **Bands:** a batch is drawn in bands of 16 rows by the caller and helper
  threads (`BLUE_RASTER_THREADS`, 3 by default counting the emulated
  processor's: more slow the emulation down more than they speed drawing
  up).
- **Speed:** pixels are unpacked and packed as whole vectors (each lane the
  same IEEE operation as one at a time), blend factors computed as vectors,
  blending by one and zero skipped, and bilinear texel addresses found
  without float clamping where the coordinates are below 2^24. That made it
  about 30% faster with the same pixels bit for bit (Unreal Tournament's
  frames replayed in one thread, 40-42 to 29 ms; Quake III's demo 9.5 to
  7.0 ms). Snapping and integer edges made it 5-27% faster again.
- **Layout matters:** the fields the row loops read stay near the start of
  `raster_state`, within reach of AArch64's paired and unscaled loads (252
  and 255 bytes); new state that isn't read per pixel goes at the end
  (`struct raster_lod`). Sixteen bytes more in each unit's fields once cost
  Quake III 0.15% more host instructions with no new work per pixel.

### The GPU backend

`src/gpu.c` draws the same commands with OpenGL 3.3 core (4.1 core on
macOS, which Apple implements on Metal on Apple silicon: `3d: drawing with
OpenGL 4.1 Metal - 91.7 (Apple M5)`).

- **When:** in real time (the window, or `--headless --realtime`), if the
  host has hardware-accelerated OpenGL 3.3. Instruction-time runs keep the
  software rasterizer, so they stay the same on every host. `--no-gpu` or
  `BLUE_GPU=0` turns it off; `BLUE_GPU=1` uses it in any run, software
  OpenGL such as Mesa's llvmpipe included.
- **Loaded at run time** (`src/gl.c`), as SDL2 is, so it's no build
  dependency: `gl.c` declares the parts of the GL, EGL and CGL ABIs it
  uses, and both platforms' code is built on every host. On macOS, CGL from
  the OpenGL framework: a 3.2 core profile (which gives 4.1), accelerated,
  no recovery to Apple's software renderer, offline renderers allowed and
  automatic graphics switching, so an off-screen context doesn't wake a
  discrete GPU. On Linux, `libEGL.so.1` on a display without a window
  system (Mesa's surfaceless platform, then EGL's device platform for
  NVIDIA's driver, then the default display), so it works the same under
  X11, Wayland or none; a 3.3 core context, current without a surface or
  with a 1 x 1 pbuffer; functions from `eglGetProcAddress`, else
  `libOpenGL.so.0` or `libGL.so.1`.
- **Its own context on its own thread,** rendering into framebuffer
  objects: it never touches the window's SDL renderer (SDL's OpenGL
  renderer on Linux keeps track of the current context itself, and GLVND
  won't make an EGL context current on a thread with a GLX one). Jobs go
  to the thread one at a time; a job is done when its OpenGL calls are
  made, and only reading back waits for the GPU, so the GPU draws a batch
  while the guest records the next. The thread starts at boot and opens
  the context in the background; the first 3D context waits for it, and
  says which backend draws.
- **Accepted only if** the context is OpenGL 3.3 core or later; the
  renderer isn't a software one (llvmpipe, softpipe, swrast, "Software
  Rasterizer", "Apple Software Renderer", SwiftShader; virtual GPUs that
  pass drawing to the host's count as hardware), unless `BLUE_GPU=1`;
  textures and renderbuffers can be 4,096 pixels across (RAVE's largest
  context) and 32-bit float depth makes complete framebuffers; the
  programs compile; and a built-in scene drawn by both backends comes out
  the same within the tests' tolerance. A broken driver is caught there,
  before the guest sees it.
- **Coordinates:** vertices map to clip space with w = 1, so the GPU
  interpolates linearly in screen space as `raster.c` does, and divides
  texture coordinates per pixel as it does. The varyings are declared
  `smooth`, the same with w = 1 as `noperspective`: Mesa's llvmpipe
  interpolates `noperspective` ones wrongly where it clips a triangle at
  the target's edges, which OpenGL's triangles reach. Image row y is GL
  row y (drawn upside down, read back the right way up). `GL_DEPTH_CLAMP`
  is on.
- **Depth:** `GL_DEPTH32F_STENCIL8`. For z, the depth is `gl_Position`'s,
  so the GPU tests it early; for perspective z, the fragment shader writes
  1/w / (1 + 1/w), monotonic in 1/w (like a reversed z, it keeps float
  precision for distant geometry), with the comparisons turned round.
- **A program per way of drawing**, made the first time it's needed (a
  few milliseconds): `raster.c`'s fragment work step by step, with the
  state's stages compiled in, and variants for bitmaps, pixel rectangles,
  perspective z, projective and 3D textures, coverage (OpenGL's smooth
  points and lines), the polygon stipple and the LOD bias. Settings within
  a program are uniforms, set when the state changes.
- **Batching:** each job's commands become one vertex array, cut into
  draw calls where the state, the program or the kind of primitive changes
  or a clear comes between; it's uploaded once (`GL_STREAM_DRAW`) and drawn
  in order, so blending and depth see the commands in order. The blend
  equation and colour are set only when they change: set for every draw,
  even to the same values, they cut a test of many small draws to a fifth
  of its frame rate on Apple's driver.
- **Textures** are uploaded the first time a batch uses them, as
  `GL_RGBA8` from the host's words; the texels stay on the host for the
  fallback. A mipmap level whose size isn't half the one before (rounded
  down) ends the GPU's chain there, as it would make the texture
  incomplete. Samplers cover the filters and clamping, with anisotropic
  filtering (at most 8) where the driver has it. The GPU picks mipmap
  levels per pixel (trilinear with the `*_MIPMAP_LINEAR` filters, and
  RAVE's Best texture filter), which looks better than one level per
  triangle and only happens in real time.
- **Points, lines and bitmaps** are quads that `raster.c`'s own arithmetic
  places on whole pixels (each OpenGL fragment's square from
  `raster_gl_fragments()`; RAVE's lines a square a step), so they come out
  as in software. Logic operations are OpenGL's own (macOS's OpenGL 4.1 on
  Metal does them, each operation's bits as OpenGL has them).
- **Reading back:** at the end of a frame `glReadPixels` reads the whole
  target into the host buffer `raster.c` would have drawn into (1.2 MB at
  640 x 480, 5 MB at 1280 x 1024), and the frame is presented from there as
  a software one is; depth and stencil are read back only when OpenGL reads
  or copies them. On an M5 that's nearly free with the shared memory: most
  of its cost in a game is the GPU finishing the frame at the low clocks
  macOS gives it between frames (a whole frame drawn and read back at full
  clocks takes 0.5-0.9 ms).
- **Failing:** if OpenGL can't be loaded or isn't accepted, the reason is
  printed once and everything draws in software. Later, `glGetError` after
  every job and framebuffer completeness when a target is made catch
  failures; then every GPU target is freed, that frame is lost, and the
  rest of the run (restarts included) draws in software. `BLUE_GPU_FAIL=N`
  fails the Nth job, to test that; `BLUE_GPU_DEBUG=1` logs each job and
  the shaders' logs. (A driver that put a SIGSEGV handler of its own in
  front of the JIT's could swallow fastmem's faults; Blue doesn't check
  for one. `BLUE_JIT_FASTMEM=0` does without those faults.)

Its pixels are `raster.c`'s but for these, in real time only:

1. **Edges:** a GPU with another subpixel grid, or one that rounds a
   vertex the other way, can give a pixel whose centre is on or very near
   an edge to the other triangle. Shared edges stay watertight.
2. **Interpolation:** colours, texture coordinates and fog can differ by a
   unit in the last 8-bit place; bilinear filtering weighs texels with a
   few bits of fraction (often 8) where `raster.c` uses floats.
3. **Transparent fragments that add colour:** with the premultiply or
   factor blends, a fragment of alpha 0 with some colour is drawn by both,
   but only the GPU writes its depth (it can't skip the write per
   fragment). QuickDraw 3D turns depth writes off for transparency.
4. **Depth:** z outside 0 to 1 is clamped; perspective z is 1/w / (1 + 1/w)
   in float, not -1/w, so near-coincident surfaces can resolve otherwise.
5. **Mipmapping** per pixel, and chains of odd sizes cut short.

Speed, on an M5, whole frames read back, textured, fogged and a fifth
blended: at 640 x 480 the GPU drew 366 frames a second against the
software rasterizer's 153, 4.6 times as many at 1024 x 768 and 5.1 at
1280 x 1024 (6.6 with 10,000 triangles a frame), and the rasterizer's
helper threads are free.

### Presenting and pacing

A frame is presented into guest memory: RAVE's into its device, clipped
to its clip region's bounding box; OpenGL's into a window's or the
screen's port, clipped to the port's `visRgn` and `clipRgn` themselves
(QuickDraw's region format walked row by row, `src/surface.c`), into the
whole screen, or into an offscreen buffer (alpha kept). OpenGL's 16-bit
frames are dithered while `GL_DITHER` is on (below).

Frames for the screen come at most one a vertical blank of the display's
(60 a second of guest time; `frame_paced()`, `frame_shown()` and
`frame_wait()` in `src/nk.c`): a context drawing to a screen shows a frame
at most once a vertical blank interval after its last, and the call that
ended it (RAVE's first `QARenderEnd` or `QASwapBuffers` after a
`QARenderStart`; OpenGL's `aglSwapBuffers` to a window's or the screen's
port, each context a frame source of its own) returns then. In real time
it leaves the host call without moving the PC, so the guest takes
interrupts and makes the call again, which naps (Multiprocessing Services'
tasks run first) until the frame's time, without making up the lead guest
time may have over the host clock as idling does (the game would show
it). In instruction time guest time moves on instead. Offscreen swaps
aren't paced.

Games of the time go wrong at the frame rates a host's GPU reaches.
Unreal Tournament's engine (`ULevel::Tick`) clamps each tick it gives the
actors to 0.005-0.4 s, so above 200 frames a second its actors, their
timers and the match clock ran fast: at 400 frames a second, twice the
speed (a match's Elapsed Time 66 s in 30 s of host time at 640 x 480 on
9.2.2). Paced, it plays at 60 frames a second, 30 s in 30 s, and the host
sleeps about half the time while it plays. A real iMac drew UT at well
under 60.

In a window in real time, the window shows each paced frame when it's due,
rather than at its own next update, which ran a little slower than 60 a
second: a frame was shown twice and the next never every few seconds (0.8%
of Quake III's frames). Frames now come 16.67 ms apart (99th percentile
16.91 ms), none lost.

## Blue's OpenGL

### What Mac OS 9 has

Apple's OpenGL for Mac OS 9 is 1.2 with 9.1 and 1.2.2 with 9.2.2 (9.0's
was 1.1.2, by accounts of the time); 8.5 and 8.6 have none (Apple offered
it as a download). 9.1's
installer carries six files (read from its Installation Tome with the
`arc-mac` crate's tome reader; each `vers` "1.2, Copyright Apple Computer,
Inc. 1999-2000"), all `shlb`s:

| File | Creator | Data fork | Exports | Imports |
|---|---|---|---|---|
| OpenGLLibrary | `opgl` | 218,148 | 474: 440 `gl`, 33 `agl`, `glc_cc` (data) | OpenGLMemory 4, InterfaceLib 40, OpenGLProfiler 35 (weak) |
| OpenGLEngine | `gli1` | 711,795 | 17 `gli` | OpenGLMemory 11, MathLib 6, InterfaceLib 7 |
| OpenGLMemory | `glm1` | 10,370 | 25 `glm` | DriverServicesLib 2 (weak), InterfaceLib 6, MPLibrary 2 (weak) |
| OpenGLUtility | `glu1` | 214,786 | 51 `glu` | MathLib 6, OpenGLLibrary 24, InterfaceLib 3, OpenGLMemory 3 |
| OpenGLRenderer | `gld1` | 2,833,014 | 22 `gld` | OpenGLMemory 3, MathLib 2, GLSystem 15 |
| OpenGLRendererATI | `gld1` | 278,388 | 22 `gld` | InterfaceLib 9, MathLib 2, QuickDraw™ 3D Accelerator 12, OpenGLMemory 5 |

How they fit (from their code):

- **OpenGLLibrary** is the API: OpenGL 1.1, 1.2's additions (the 3D
  textures, `glDrawRangeElements`, the imaging subset), the entry points of
  `ARB_multitexture`, `ARB_transpose_matrix`, `ARB_texture_compression`,
  `EXT_blend_color`, `EXT_blend_minmax`, `EXT_compiled_vertex_array` and
  `EXT_secondary_color`, and all 33 of AGL (there's no separate AGL
  library). 432 of the 440 gl functions are short wrappers: they load
  `glc_cc` (the current context, a data export), pass the context's first
  word first and call through a table in the context at a fixed offset
  (`glAccum` at +0x4 ... `glResetMinmax` at +0x6D8), in the order of Mac OS
  X's `GLIFunctionDispatch` (`gliDispatch.h`), since Mac OS X's OpenGL
  descends from this one. `aglSetCurrentContext` stores the context in
  `glc_cc`. OpenGLLibrary loads the engine at run time.
- **OpenGLEngine** (the `gli` interface) keeps the state and, going by its
  size and imports, transforms and lights. It finds renderers by walking a
  folder for files of creator `gld1`, and hands them transformed vertices
  through the 22-function `gld` interface, which is private and
  undocumented.
- **Renderers:** Apple's generic software renderer (ID 0x00020200: vendor
  "Apple", renderer "Generic", version "1.1"; window, offscreen, backing
  store, MP safe, robust, multiscreen and compliant, not accelerated or
  full screen; accumulation buffers RGB 888, ARGB 8888, RGB 16-16-16 and
  ARGB 16-16-16-16; 4 auxiliary buffers), and ATI's (ID 0x00021000:
  accelerated, full screen, compliant; no accumulation buffer, no stencil,
  not offscreen), which draws through ATI's RAVE engines with private
  gestalt selectors, about 50 private tags and `accessDrawBuffer`. Its
  renderer names and extensions go by the chip: "Rage 128 OpenGL Engine"
  for a Rage 128, whose list is `GL_ARB_multitexture GL_ARB_texture_env_add
  GL_EXT_compiled_vertex_array GL_EXT_texture_env_add GL_EXT_abgr
  GL_EXT_bgra GL_EXT_texture_env_combine GL_EXT_texture_lod_bias
  GL_SGIS_texture_edge_clamp` (a Rage II's has no multitexturing, a Rage
  Pro's no combine or edge clamp; the Radeons' add
  `GL_EXT_texture_filter_anisotropic`).
- **The engine's `glGetString`** passes the renderer's vendor, renderer
  and version on, and makes the extensions its own seven
  (`GL_APPLE_specular_vector GL_APPLE_transform_hint GL_APPLE_packed_pixel
  GL_ARB_transpose_matrix GL_EXT_clip_volume_hint GL_EXT_rescale_normal
  GL_NV_texgen_reflection`) followed by each of the renderer's it knows,
  in the renderer's order, each with a space after it.
- **None of 9.2.2's lists has S3TC or paletted textures:** only the
  "NVIDIA OpenGL" engine on the same disk, for GeForce cards, offers them.
  Nor does Mac OS 9 have fog coordinates: OpenGLLibrary exports
  `glSecondaryColor*EXT` (for separate specular and `GL_COLOR_SUM_EXT`) but
  no `glFogCoord*`, and the engine lists neither extension.

### Why Blue replaces the libraries

Blue provides OpenGLLibrary, OpenGLMemory and OpenGLUtility itself, under
Apple's fragment names and with Apple's exports, and doesn't load Apple's
engine or renderers. The alternatives were a renderer under Apple's engine
(its `gld` interface is private, transform and lighting would stay in
emulated PowerPC code, and it would work only where Apple's OpenGL is
installed), Apple's OpenGL over Blue's RAVE engine passing for ATI's (much
private ATI interface to learn, and OpenGL 1.1 at most), and replaying the
calls on a compatibility-profile context on the host (the least code, but
no reproducible software path: Mesa's llvmpipe differs between versions
and macOS has none). Replacing the libraries gives:

- speed: no OpenGL engine running as emulated code, and vertices
  transformed on the host;
- the same on 8.5 and 8.6, which have no OpenGL, as on 9.x: Unreal
  Tournament's OpenGL build runs on an 8.6 install as it is;
- one deterministic software path, and the backend RAVE uses;
- Blue's own say over the identity, extensions and limits.

The price is OpenGL 1.2's fixed function, written in C, which is most of
the work; Mesa's compatibility profile serves as the oracle in the tests.

### The libraries

They're generated code fragments (`src/opengl.c`, by the fragment builder
in `src/ndrv.c`) from one table of the 474 + 25 + 51 functions with their
C signatures, `src/opengl_table.h`, which `tools/gltable.py` made from
Mac OS 9.2.2's libraries (the exports, and the dispatch table's offset
each gl wrapper calls through, read from its code) and the macOS SDK's
headers. On the tools volume they're "Blue OpenGL Library", "Blue OpenGL
Memory" and "Blue OpenGL Utility" (type `shlb`, creator `syGL`), with
Apple's versions (current 1, oldest compatible 0): programs linked against
Apple's accept them (Unreal Tournament's OpenGL build imports them with
versions 0 and 0, all weak).

- **The fragment builder** makes any number of entries and exports, found
  through a hash table as PEF linkers lay it out (`PEFHashTableIndex`,
  checked against all 474 of Apple's OpenGLLibrary's exports), data exports
  (`glc_cc`), code of a fragment's own for chosen entries, zero-filled data
  after the initialized, and initialization and termination routines.
- **Host calls** see f1 to f13 as well as r3 to r10, and `ndrv_args()`
  walks a call's arguments where the Mac OS (AIX-style) calling convention
  puts them: integers and pointers take the next word (r3-r10, then the
  caller's parameter area at 24(r1)), floats and doubles the next of f1 to
  f13 and skip one or two words too.
- **Each process has its own instance** of OpenGLLibrary's data: its
  contexts, pixel formats, renderer infos, the recording buffer and the
  strings it hands out; the initialization and termination routines start
  and end the instance on the host.
- **Contexts are laid out as Apple's:** word 0 a handle (the context's own
  address), then 441 dispatch table slots from +0x4 to +0x6E4, each calling
  its gl function with the handle first. The order is Mac OS X's but for
  +0x544 (`glBlendFuncSeparate` there, which Mac OS 9 doesn't have: it does
  nothing) and +0x650 and +0x654, which are `glBlendColor` and
  `glBlendEquation`. `glc_cc` is exported as Apple's is, so programs that
  call through the table work too.
- **OpenGLMemory** allocates with `NewPtr`, `NewPtrClear`, `GetPtrSize`
  and `DisposePtr` through callouts; its fills and copies are done on the
  host; modes and settings are accepted.
- **The data carries its version** (8), which moves whenever the
  fragment's data changes: one installed by an older Blue is left alone
  (every call fails), and Blue says to update it.
- **Installing:** with the other guest tools; on Mac OS 9, Apple's
  same-named libraries go to Extensions (Disabled) while Blue's are in
  Extensions, rather than leaving the Code Fragment Manager to choose
  between two fragments of one name (see
  [guest-tools.md](guest-tools.md#offering-and-installing-them)).

### Recording in guest memory

A kernel exit costs about 50 ns. So that immediate-mode drawing doesn't pay
one per call, 317 of the 440 gl functions aren't host calls: those that
return nothing and take only values, or values and then one array whose
size their name gives (the `v` forms of `glVertex`, `glColor`, `glNormal`,
`glTexCoord`, `glMultiTexCoord*ARB` and the like, `glLoadMatrix`,
`glMultMatrix`), have code of the library's own (`record_code()`) that
appends a record to a 64 KB buffer in the process's instance: a word, the
function's entry << 16 | the record's size, then the arguments, each
integer a word as its register (or the parameter area) had it, each float
the 4 bytes `stfs` stores, each double its 8. `glVertex3f` records in 13
instructions. The library is built twice, once for its data's layout and
once with the code.

- **A host call** does what's recorded first, in order, on the host, so
  state and errors come out as if every call had been one; so do a full
  buffer and the first call (before the initialization routine has set the
  buffer's bounds), which make the same record from the registers. Calls
  through a context's dispatch table are recorded too if it's the current
  context.
- **Not recorded:** what returns something (`glGet*`, `glIsEnabled`,
  `glGetError`, `glGenTextures`, `agl*`), reads or writes client memory of
  any size (`glTexImage*`, `glDrawPixels`, `glReadPixels`), `glFlush` and
  `glFinish` (which show the frame), and what reads arrays there and then
  (`glArrayElement`, `glDrawArrays`, `glDrawElements`,
  `glDrawRangeElements`, `glLockArraysEXT`): a record of an index would
  read the arrays later.
- **Floats** are exact: `stfs` truncates rather than rounds, but the
  callers' floats are floats already, and the host reads them as `stfs`
  would.
- **What it costs:** about 15 PowerPC instructions a record, some 0.3 ms
  of guest time a frame in Unreal Tournament's match and less in Quake
  III. Quake III makes about 670 calls, 1,040 records and 3,400 primitives
  a frame; UT's match about 5 calls (its lists and arrays are recorded) and
  6,000-9,000 records for 800-1,000 primitives. In Blue's test application's
  triangle scene a frame's 49 calls make one host call, the swap.

### The front end

`src/glfront.c` and its companions do OpenGL 1.2's fixed function on the
emulation thread, as the records and host calls come: the state (so
`glGet*` and `glGetError` are answered at once, from it), the matrix
stacks, vertex assembly, transform, lighting, clipping and culling. Out
come screen-space points, lines and triangles, each with the backend state
that draws it (made again only when the state changes), into the
context's surface (`src/surface.c`), whose batches the backend draws in
the background.

- **The same numbers on every host:** built without fused multiply-adds,
  and with sines and cosines of its own (series in doubles after exact
  steps of 90 degrees). Matrices are floats with Mesa's formulas
  (`glFrustum`'s and `glOrtho`'s arguments made floats first); stacks are
  32 deep for the modelview and 8 for the projection and each texture
  unit.
- **Primitives:** all ten modes, with OpenGL's provoking vertices for flat
  shading; clipping in clip coordinates against the near and far planes,
  and against the others only past a guard band of 4 view volumes (the
  rest is the viewport's pixels, cut by the scissor box); user clip planes
  (6) exactly; culling by each triangle's area in window coordinates;
  polygon modes (a polygon's own edges, edge flags honoured) and polygon
  offset (the depth slope times the factor plus the units times the
  drawable's depth resolution).
- **Where OpenGL leaves room, the Rage 128's way** (as far as it's known;
  `glfront.h`): colours interpolated linearly in screen space (the chip's
  setup corrected texture coordinates for perspective, not colours);
  primitives partly off the screen drawn from their own vertices within the
  guard band, as hardware with one drew them; quads split as (v0, v1, v3)
  and (v1, v2, v3), as Mesa's software rasterizer of the time did (today's
  llvmpipe splits them the other way, which differs only where a quad's
  colours aren't linear in its position); `GL_CLAMP` clamping to the edge
  texels (the chip had no texture borders); textures kept at 8 bits a
  component whatever internal format is asked for.
- **Lighting** (`src/gllight.c`), per vertex in eye coordinates, as
  OpenGL 1.2's 2.13.1 has it (the Rage 128 had no transform engine: its
  OpenGL lit on the processor too): 8 lights (directional, positional,
  attenuated, spots), front and back materials, the light model's ambient
  colour, local viewer, two sides and separate specular (the secondary
  colour added after texturing, as a stage), the colour material, normals
  by the modelview's inverse transpose with `GL_NORMALIZE` and
  `GL_RESCALE_NORMAL`. Powers are libm's in doubles, rounded to floats.
  With `GL_APPLE_specular_vector`'s light model on, each light's specular
  term takes the light's reflection toward the eye in place of n · h, as
  Apple's specification and 9.2.2's engine have it.
- **Fog** by each vertex's eye-space |z| (there are no fog coordinates on
  Mac OS 9), the factor per pixel; **texture coordinate generation**
  (object and eye linear, the sphere map, `GL_NV_texgen_reflection`'s
  normal and reflection maps) and the texture matrices; q divided per pixel
  only for primitives whose q isn't 1.
- **Textures** (`src/gltex.c`): objects shared between contexts made to
  share; 1D, 2D and 3D images (3D up to 128 texels a side) in every format
  and type of OpenGL 1.2, packed ones, BGR, BGRA and `GL_ABGR_EXT`
  included, read big-endian from guest memory through the pixel store;
  texels kept as 8-bit ARGB as the base format gives them; completeness as
  1.2 has it. The backend's copy is made when one is first drawn, sharing
  the texels, and retired by a change. Two units, each environment
  (`GL_REPLACE`, `GL_MODULATE`, `GL_DECAL`, `GL_BLEND`, `GL_ADD`, and
  `GL_EXT_texture_env_combine`'s five functions as Apple's engine takes
  them) made the backend's stages for each base format as 1.2's table
  3.18 has it. The LOD bias (per unit, clamped to 10, the deepest level)
  and `GL_TEXTURE_MIN_LOD` and `_MAX_LOD` are added and applied to the
  level of detail before the level is chosen, in software per triangle and
  line, on the GPU as `texture()`'s bias and a sampler's limits.
- **Points and lines by OpenGL's rules** (1.2's 3.3 and 3.4;
  `raster_gl_fragments()`): aliased lines by the diamond-exit rule (ties
  broken as OpenGL's perturbed endpoints break them), wide ones as columns
  or rows of the width rounded, points as squares of the size rounded,
  sizes and widths 1 to 64. Antialiased, each fragment's alpha is times
  its coverage of the pixel (by a disk sampled 16 x 16 a pixel, or exactly
  by the line's rectangle); the hints change nothing, as with Apple's ATI
  renderer, which always asked RAVE for its best antialiasing. The line
  stipple's counter goes on by fragments along strips and loops, and starts
  again at each separate line and `glBegin`; the polygon stipple is 32 x 32
  bits by window position. Textured lines take their level of detail from
  the texels along them.
- **Client arrays** (`src/glarray.c`): every type OpenGL 1.2 takes for
  each, big-endian in the program's memory, interleaved arrays, the draw
  calls and compiled arrays, drawn as `glArrayElement` between `glBegin`
  and `glEnd` would be; the bytes the elements take are checked before
  they're read.
- **Display lists** (`src/gllist.c`): kept on the host with the bytes the
  calls' pointers pointed to (and, for images, the pixel store as it
  was), array draws as the attribute calls they make; 64 deep; shared as
  textures are.
- **Pixels** (`src/glpixel.c`): the raster position, `glBitmap`,
  `glDrawPixels` and `glCopyPixels` of colours, depth and stencil (zoomed
  either way, through the pixel transfer and the ten pixel maps), drawn as
  fragments through the per-fragment operations; `glReadPixels`,
  `glCopyTexImage`, `glCopyTexSubImage` and `glGetTexImage`. Images go from
  the raster position rounded to the nearest pixel corner, as Mesa does;
  fractional and negative zooms keep 1.2's rectangles.
- **Also:** stencil, logic operations, the attribute stacks
  (`src/glattrib.c`, 16 deep), selection and feedback (`src/glselect.c`:
  primitives clipped to the view volume, hit records and every feedback
  type, polygons as triangles in Mesa's order), evaluators
  (`src/gleval.c`: one- and two-dimensional maps of every kind, grids,
  meshes as quad strips, made normals), and the accumulation buffer, on the
  host, for the generic renderer's pixel formats (below).
- **Dithering:** while `GL_DITHER` is on, a 16-bit drawable's frames are
  dithered as they're written into guest memory, by a 4 x 4 ordered
  (Bayer) matrix by the pixel's place: each component's 5 bits are
  v x 31 / 255 + (2t + 1) / 32 rounded down, t the matrix's 0 to 15. The
  Rage 128's own matrix isn't known; a 4 x 4 ordered dither is what chips of
  its generation did. A table makes it cheap (a 640 x 480 frame in 0.13 ms
  rather than 0.05 on an M5). 32-bit drawables and RAVE's frames aren't
  dithered.

### AGL and presenting

- **Two renderers.** ATI's, "Rage 128 OpenGL Engine" (ID 0x00021000,
  accelerated, 32 MB of video and texture memory, window, full-screen and
  offscreen drawables, single and double buffers, depth 16, 24 or 32, an
  8-bit stencil, RGB 555 and 888; the stencil and offscreen drawables are
  more than Apple's ATI renderer offered, but Blue draws them). And for
  pixel formats asking for an accumulation
  buffer, which on 9.2.2 only Apple's generic software renderer had, that
  one (ID 0x00020200, not accelerated, 8 or 16 bits a component), drawn
  the same way but saying what Apple's said: so games that ask for
  `AGL_ACCELERATED`, ATI's ID or a full screen don't get one, as they
  didn't on a Mac. `aglQueryRendererInfo` lists ATI's first.
- **`aglChoosePixelFormat`** takes RGBA formats on 16- and 32-bit devices
  (the main device if none are given) and refuses auxiliary, stereo and
  multisample buffers, other renderer IDs and 8-bit screens (games switch
  to thousands or millions of colours).
- **Drawables:** a window's port (its `portRect`, or `AGL_BUFFER_RECT`'s
  rectangle), read from the `CGrafPort` in guest memory at each swap, so no
  callouts; an offscreen buffer; or the whole screen. `aglSetFullScreen`
  switches the display with the Display Manager (`DMSetDisplayMode`, by a
  callout) to the mode of exactly the size asked for, as the AGL reference
  has it, and back when that context's drawable goes (another drawable,
  none, the context destroyed, the process quitting). Apple's 9.2.2 hands
  the size to its engine and renderer, none of which imports a Display
  Manager call. Most games go full screen with DrawSprocket instead and
  draw to its front buffer's port, as Unreal Tournament does.
- **Swaps:** `aglSwapBuffers` (or `glFlush` and `glFinish`,
  single-buffered) draws what's recorded and presents the frame
  ([above](#presenting-and-pacing)); swap rectangles are honoured and the
  swap interval kept.
- **`aglUseFont`**, as Apple's: QuickDraw draws each glyph into a 1-bit
  offscreen world (the font, face and size set, measured by
  `GetFontInfo`), by callouts, and the host makes list base + i a
  `glBitmap` of (CharWidth + 2e) x (ascent + descent + 2e) from
  (e, descent + e - 1), moving CharWidth on, e being half the size for a
  styled face. OpenGLLibrary imports those calls from InterfaceLib, as
  Apple's does.

### Identity and extensions

`GL_VENDOR` "ATI Technologies Inc.", `GL_RENDERER` "Rage 128 OpenGL
Engine" (Apple's own strings) and `GL_VERSION` "1.2 Blue": the RAVE engine
tells games it's a Rage 128 too, programs parse the version's leading
number, and games look at the renderer for quirks (Unreal Tournament picks
`OpenGLDrv.ini` sections by vendor and renderer; Quake III treats a Rage
Pro specially). `GL_MAX_TEXTURE_SIZE` is 1024, with 2 texture units, 8
lights, 6 clip planes and 8 stencil bits.

`GL_EXTENSIONS` is 9.2.2's engine's list, in its order, of what Blue does,
as a Rage 128 had it: `GL_APPLE_specular_vector GL_APPLE_transform_hint
GL_APPLE_packed_pixel GL_ARB_transpose_matrix GL_EXT_clip_volume_hint
GL_EXT_rescale_normal GL_NV_texgen_reflection GL_ARB_multitexture
GL_ARB_texture_env_add GL_EXT_blend_color GL_EXT_blend_minmax
GL_EXT_blend_subtract GL_EXT_compiled_vertex_array GL_EXT_texture_env_add
GL_EXT_texture_env_combine GL_EXT_texture_lod_bias GL_EXT_abgr GL_EXT_bgra
GL_SGIS_texture_edge_clamp`. The generic renderer's contexts give "Apple",
"Generic", "1.1" and the extensions 9.2.2's engine made of its renderer's
(all but `GL_EXT_compiled_vertex_array` and `GL_EXT_texture_env_combine`,
in that renderer's order, ending with a space); their functions are the
same. Details follow Apple's engine where the specifications leave room or
it departs from them: it keeps a LOD bias as given and answers no
`GL_MAX_TEXTURE_LOD_BIAS_EXT` (Blue answers 10, as the extension
recommends), and it takes only `GL_EXT_texture_env_combine`'s values,
refusing a scale other than 1, 2 or 4 with `GL_INVALID_ENUM`.

### OpenGLUtility

`src/glu.c` does OpenGLUtility on the host as SGI's GLU 1.2 does it
(Apple's is SGI's, "1.2 MacOS 8.0"), by gl calls to the current context, so
display lists keep what it draws: the matrices (`gluOrtho2D`,
`gluPerspective`, `gluLookAt`, `gluPickMatrix`), `gluProject` and
`gluUnProject`, `gluScaleImage`, 1D and 2D mipmaps, and the quadrics
(spheres, cylinders, disks and partial disks in each style, flat or smooth,
either way out, textured), with Apple's strings and errors. Like Apple's,
it imports OpenGLLibrary's `glc_cc` to find the current context, and its
objects are blocks from the program's Memory Manager (`NewPtrClear`, by a
callout).

- **Quadrics** are SGI's call for call (compared with Mesa's libGLU, which
  is SGI's code), but where SGI's reads normals it never computed (flat
  ones for points and silhouettes: stale stack memory, a previous call's in
  Mesa's), Blue gives the smooth ones.
- **Mipmaps** go through 16-bit images, each level the last one scaled, as
  1.2 does. Mesa's libGLU is 1.3, which keeps 2D images in their own type,
  halving 8-bit ones directly and scaling the rest by another box filter:
  up to 35 levels apart from 1.2's at the first level of a 3 x 7 image, and
  within a level where there's no scaling.

### What it leaves out

OpenGLUtility's tessellators and NURBS renderers keep their objects and
properties but draw nothing; `GL_POLYGON_SMOOTH` is kept but polygons
aren't antialiased; pixel formats asking for auxiliary buffers are refused
(the generic renderer had 4); there's no colour index drawing (Apple's
renderers drew RGBA on 16- and 32-bit screens, and Blue has no 8-bit
pixel formats); and the imaging subset's convolution, histogram and
minmax give `GL_INVALID_OPERATION`, with `GL_ARB_imaging` not offered.
S3TC and paletted textures aren't offered, as Apple's 9.2.2 didn't for a
Rage 128. Programs that call OpenGLEngine's `gli` functions, or poke at
Apple's private context fields, aren't handled. The
[roadmap](roadmap.md) has these, for when a program needs them.

## Testing

- **The backends:** `tests/test_raster.c` checks the rasterizer's
  coverage, stages, blending, stencil, logic operations, lines and points
  as OpenGL draws them, and a mesh with edges through pixel centres
  (`test_shared_edges`); `tests/test_gpu.c` draws the same on the GPU
  against `raster.c`: exactly where GPUs agree with it (whole-pixel
  geometry, depth in both modes, texture orientation, clears, points,
  lines, bitmaps, copies, the LOD bias and range), and within a step
  elsewhere. 20 random streams of RAVE calls (6,000 frames, 3 million
  triangles, every kind of call and state) give the same pixels in
  software on macOS and Linux, on ARM and x86-64, and the GPU's frames of
  them are checked too.
- **Against Mesa:** on Linux, `tests/test_opengl.c` draws scenes through
  the libraries (their records and host calls, vectors and arrays in guest
  memory) in software and on the GPU, and by Mesa's own OpenGL
  (its compatibility profile, llvmpipe, a framebuffer object of EGL's
  surfaceless platform), and counts the pixels of 6,912 that differ by
  more than 2. Most scenes differ by 2 at most. Where they don't, it's
  Mesa's way, not OpenGL 1.2's or the Rage 128's: Mesa corrects colours for
  perspective ("smooth": 2,739 pixels), blends `GL_CLAMP` with the border
  colour ("clamp": 3,840), and in Mesa 25.2 continues the line stipple's
  counter by segments' lengths, draws smooth lines' alpha as a ramp and
  smooth points as round aliased ones, steps libGLU's lines at other points
  ("glu", compared when `BLUE_TEST_GLU` names `libGLU.so.1`), and lights a
  back face a few levels apart. Feedback and selection give Mesa's records
  within 1e-3.
- **Where Mesa 25.2 departs from OpenGL 1.2,** Blue keeps OpenGL's way, the
  scenes avoid the difference, and `tests/test_glfront.c` checks OpenGL's:
  pixel rectangles at fractional and negative zooms; feedback's
  `GL_LINE_RESET_TOKEN` (Mesa gives `GL_LINE_TOKEN`) and flat-shaded colours
  (Mesa gives each vertex's own); after a colour map is evaluated, the
  current colour (Mesa loses the components the last `glColor` didn't
  set); filled meshes as quad strips (Mesa's are triangle strips);
  `glGetMap`'s order; a backwards domain's normals. Mesa 25.2's
  `glDrawPixels` with `GL_MAP_COLOR` frees a block it goes on using, which
  corrupts its heap (a few calls to Mesa alone abort): the harness fails a
  scene that turns pixel maps on rather than run it.
- **On radeonsi** (Mesa 26.2 on a Radeon RX 6800 XT, x86-64 Linux, gcc and
  clang): everything passes, the GPU backend within 1 of software. Tests
  must keep off ties: a pixel centre exactly on a texel's edge, an alpha
  exactly at the test's reference, a depth exactly another's, a clear of
  0.1 (25.5 of 255) or a gradient under a logic operation pass on one GPU
  and fail on another, as the last bit of a division or interpolation
  decides. Two things of radeonsi's own are left out there: its
  `glCopyPixels` of depths writes no colour and writes depth with the depth
  test off, and it draws an aliased point of size 2.6 2.6 pixels across,
  where OpenGL 1.2 rounds the size to 3.
- **In the guest:** Blue's test application, Blue GL Test, draws its scenes
  through the guest's OpenGL as a game would, the same screenshots on
  macOS and Linux in instruction time and within a step or two on the GPU
  (see [building.md](building.md#testing-the-guests-opengl)). The recording
  code is run by the interpreter and the JIT, and each record's bytes
  checked.
- **Games:** Unreal Tournament's OpenGL build (the UT CD's `Extras:OpenGL
  UT.sea`; it imports 37 gl, 7 agl and one glm function) plays on 8.6 and
  9.2.2, and Quake III Arena's demo (id's of December 1999; it calls 61
  functions) on 8.6, on the GPU and in software; in instruction time they
  play out the same on macOS and Linux (with the same time zone: the
  guest's clock is the host's local time). Neither takes up the specular
  vector, the LOD bias or combine. Against UT's RAVE build at the same instruction counts, the
  pictures are the same, the OpenGL build's lightmapped walls a little
  brighter (UT's two renderers light differently).

## Where a frame's time goes

`BLUE_GL_PROFILE=FILE` writes a line for each OpenGL frame shown on the
screen: the host time since the one before and where it went (the
libraries' host calls, the front end's work among them; waiting for the
backend; reading back; writing the frame into guest memory; napping until
it's due), the calls, records and primitives, and the GPU thread's time
drawing and reading back; and a line at each update of the window. In real
time on an M5 (four performance cores) at 640 x 480, in milliseconds a
frame:

| | fps | frame p50 / p90 / p99 | guest | front end | waiting for the backend | reading back | presenting | napping |
|---|---|---|---|---|---|---|---|---|
| Quake III, GPU | 60.0 | 16.7 / 17.8 / 18.9 | 3.1 | 1.8 | 0.1 | 1.6 | 0.3 | 9.7 |
| Quake III, software | 59.2 | 16.7 / 17.6 / 24.2 | 1.5 | 0.9 | 6.8 | | 0.2 | 7.5 |
| UT intro, GPU | 60.0 | 16.7 / 17.3 / 18.5 | 4.5 | 0.8 | 0.5 | 1.9 | 0.4 | 8.6 |
| UT intro, software | 52.3 | 18.5 / 23.2 / 26.9 | 3.4 | 0.5 | 12.5 | | 0.3 | 2.5 |
| UT match, GPU | 60.0 | 16.7 / 18.4 / 21.6 | 3.8 | 0.3 | 0.2 | 2.3 | 0.4 | 9.7 |
| UT match, software | 59.1 | 16.7 / 17.5 / 21.8 | 1.4 | 0.2 | 9.6 | | 0.3 | 5.6 |

(Measured before the rasterizer's vector work, which took Quake III in
software to 59.9 frames a second and UT's intro to 56.8.) On the GPU every
frame is ready with 7-10 ms to spare; in software the rasterizer is the
cost. What wasn't worth doing, measured: a `glFlush` after each GPU draw
job; four rasterizer helpers rather than two (no clear gain with the
emulation as a fifth busy thread on four performance cores); bands of 8
rows; setting triangles up once a batch rather than once a band;
presenting straight to the window rather than through guest memory
(writing a frame is 0.2-0.5 ms); reading back only what changed (games
redraw every pixel); transform in a vertex shader (the front end is
0.2-1.8 ms a frame, and software needs it in C anyway); bigger batches
(waiting for the GPU is 0.1-0.6 ms a frame).

Unreal Tournament's OpenGL build draws 13-28% of the time on the GPU at 60
frames a second (its RAVE build 15%), and about 85% in software, at 41-60
frames a second in the intro and about 50 in a match.

`BLUE_RAVE_FPS=1` and `BLUE_GL_FPS=1` print the frame rate every second,
and `BLUE_LOG_RAVE=1` and `BLUE_LOG_GL=1` log every call.
